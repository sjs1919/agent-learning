## 1. 开场：培训宗旨与重要节点摘要（5 min）

### 1.1 培训宗旨（2 min）

**核心命题**：AI 工具已经普及，但"会用"和"用得好"之间差距巨大。

本课程的定位：
- **不是**教你按哪个按钮、装哪个插件
- **而是**建立一套可复用的 AI 协作方法论，让 AI 从"偶尔帮手"变成"日常搭档"

**一条主线串联全场**：

```
上半场（Prompt 精修）          下半场（项目级协作）
─────────────────────  →  ─────────────────────
写好一条 prompt              带 AI 做完一个项目
"说得清楚"                   "做得成事"
```

> Prompt 工程是写得好，协作工程是做得成。两者缺一不可。

### 1.2 重要节点摘要（2 min）

| 节点 | 内容 | 你要带走 |
|------|------|---------|
| **上半场** | 5 条铁律 + 4 种 Prompt 模式 + 模板参数化 + CLAUDE.md 入门 | 可复用的 prompt 模板 |
| **下半场·模块 1** | 多轮对话状态管理 + 大型代码库导航 | 上下文管理能力 |
| **下半场·模块 2** | AI 辅助 TDD | 测试驱动 + AI 配合 |
| **下半场·模块 3** | Claude Code 深度工作流 + 完整功能演练 | 端到端工作流 |

### 1.3 今天结束时的你（1 min）

- ✅ 遇到新需求，知道怎么拆解、怎么写 prompt
- ✅ 对话乱了，知道什么时候 `/clear`、怎么断点续传
- ✅ 大项目中，知道怎么让 AI 精准定位而不是大海捞针
- ✅ AI 写完代码，知道怎么用测试兜底

## 2. 多轮对话状态管理（12 min）

### 2.1 核心认知：对话不是无限的（2 min）

Claude Code 的上下文窗口约 200K tokens，但：

- 对话越长，早期消息的权重越低
- 超过阈值后，早期内容会被丢弃
- 症状：AI "变笨"、忘了之前的约定、重复已做过的事

### 2.2 断点续传技巧（4 min）

**问题**：一个功能开发到一半，对话上下文已经混乱，怎么办？

**传统做法**（不推荐）：
```
继续刚才的功能
```
→ AI 大概率忘了做到哪一步，需要反复确认。

**正确做法**：手动总结进度 + 开新对话

```
我们刚才完成了以下工作：
1. 在 src/api/order.ts 中创建了 createOrder 接口
2. 在 src/services/order.ts 中实现了核心逻辑
3. 待完成：联调前端表单验证 + 写单元测试

当前状态：后端接口已通，返回格式为 {code, data, message}

请继续第 3 项：在 src/views/order/ 下创建下单表单页面，
要求：
- 表单字段：product_id(下拉选择), quantity(数字), remark(文本)
- 提交后调 POST /api/order/create
- 用现有的 RePureTableBar + vxe-table 风格
```

**进阶技巧**：用文件保存进度状态

为什么需要文件而不是靠记忆？

| 方式 | 问题 |
|------|------|
| 靠 AI 的对话记忆 | 对话长了会丢，`/clear` 后全没了 |
| 靠人脑记 | 第二天就忘了做到哪一步 |
| ✅ 靠文件 | 持久化、可追溯、可交接 |

**三级进度文件体系**（来自团队 lexy-workspace 实践）：

```
tmp/
├── ai-progress.md              ← 任务全景索引（"有哪些事"）
├── ai-progress-{功能名}.md     ← 当前任务详情（"做到哪了"）
└── ai-acceptance.md            ← 验收记录（"做完了没"）
```

**使用方式**：

每次开新对话或 `/clear` 后，只需一句：

```
读 tmp/ai-progress.md 和 tmp/ai-progress-订单列表页.md，继续执行 checklist 中第一个未完成项。
```

**核心工作流**（来自 lexy-workspace 实践）：

```
任务拆分 → checklist 写入文件 → 用户确认 → AI 逐项执行 → 自验 → 用户验收 → 更新状态
    ↑                                                                    ↓
    └──────────────── 每完成一项，更新 checklist 状态 ────────────────────┘
```

> 💡 **关键原则**：每个任务开始前，用户必须确认 checklist。AI 不能自己决定"下一步做什么"。

### 2.3 `/clear` 的正确用法（2 min）

| 场景 | 做法 |
|------|------|
| 对话上下文混乱，AI 表现异常 | `/clear` 开新对话，带上项目配置文件 |
| 完成一个大任务，开始新任务 | `/clear` + 手动总结进度到文件 |
| 发现 AI 在重复之前的错误 | `/clear` 后，把之前的教训写进新 prompt |

**场景举例**：

**场景 1 — 对话混乱**：你在调一个表单校验逻辑，AI 反复建议改已经删掉的代码，或者一直提 5 轮之前讨论过的方案。

```
/clear

读 CLAUDE.md 和 src/views/order/index.vue，
当前问题是：表单提交时 email 字段校验不生效，
已确认 rules 里配了 email 规则，但 validate() 返回 true。
帮我排查原因。
```

**场景 2 — 切换任务**：刚刚完成了订单列表页的 API 联调，现在要开始写 Excel 导出功能——这是两个独立任务，继续用同一个对话会让 AI 混淆两套上下文。

```
先把当前进度写到 tmp/ai-progress.md：
- 订单列表页 API 联调 ✅
- 接下来是 Excel 导出

/clear

读 tmp/ai-progress.md 和 tmp/ai-progress-订单列表页.md，
下一个任务是 Excel 导出。参照 src/views/system/user/ 里的导出逻辑。
```

**场景 3 — 重复错误**：AI 连续两次在 Pinia store 里用了 `this.$http`（项目实际用的是 `http.request`），说明它没记住项目规范。

```
/clear

读 CLAUDE.md。
重要约定：所有 API 调用统一用 http.request<T>(method, url, config)，
不要用 this.$http 或 axios 直接调。

现在重新实现 src/store/modules/order.ts 的 fetchOrderList action。
```

**关键**：`/clear` 后，重要的项目约定不会丢失（因为 `CLAUDE.md` 会自动加载），但**当前进度会丢失**，必须手动保存。

### 2.4 用文件传递上下文（4 min）

**反模式**：把大段代码贴到对话框

```
❌ 帮我看下这段代码有什么问题：
[paste 200 行代码]
```
→ 浪费上下文窗口，AI 只能看到片段。

**正确做法**：让 AI 读文件

```
✅ 读 src/services/order.ts 中的 createOrder 函数，
分析是否有并发安全问题。
重点关注：
1. 库存扣减逻辑是否原子
2. 重复订单的判断机制
3. 事务边界
```

**文件传递 vs 对话框粘贴的对比**：

| 方式 | 适用场景 | 优点 |
|------|---------|------|
| 对话框粘贴 | 小于 50 行的片段 | 快速，AI 能直接看到 |
| 让 AI 读文件 | 超过 50 行、跨文件 | 不占用上下文窗口，AI 可以反复查阅 |
| 写进临时文件 | 进度追踪、复杂约定 | 持久化，断点续传 |

> 💡 **项目级 AI 协作，最关键的转变就是习惯使用文件来传递上下文。**
>
> 对话框是"一次性"的，文件是"持久"的。养成"先写文件，再让 AI 读"的习惯，是单次任务升级为项目级协作的分水岭。

## 3. 大型代码库导航策略（10 min）

### 3.1 先建项目地图（3 min）

**问题**：进入一个陌生的大型项目，不知道从哪开始。

**传统做法**：自己花几小时读目录结构、看入口文件。

**AI 辅助做法**：让 AI 先分析项目结构

```
先分析这个项目（当前目录）的整体结构：
1. 技术栈和框架
2. 目录组织方式
3. 核心业务模块有哪些
4. 入口文件和关键配置

用 markdown 列表输出，不要改任何代码。
```

**进阶**：让 AI 生成项目地图文件

```
基于你对项目的分析，生成一个 PROJECT_MAP.md，包含：
- 模块清单和职责
- 关键文件位置
- 数据流向
- 技术决策记录

写到 docs/PROJECT_MAP.md，后续开发时我会让你参考它。
```

**最牛逼的做法**：用 Understand-Anything 自动生成项目知识图谱

手写 PROJECT_MAP.md 的问题：写一次要几小时，代码一改就过时，大型项目根本维护不了。

[Understand-Anything](https://github.com/Lum1104/Understand-Anything) 是一个开源工具，用多智能体 + 语法树静态分析，自动把整个项目转成一张**可交互的知识图谱**：

| 能力 | 做了什么 |
|------|---------|
| **自动扫描** | 遍历全部文件，识别语言、框架、模块结构 |
| **结构提取** | 用 tree-sitter 提取函数/类/接口/导入关系（确定性，不靠 LLM 猜） |
| **语义分析** | LLM 给每个节点生成中文摘要、标签、复杂度评估 |
| **架构识别** | 自动划分 3-10 个架构层（API 层、Service 层、Data 层等） |
| **学习路径** | 生成 5-15 步引导式导览，按依赖顺序带你读懂项目 |
| **可视化** | 启动一个 Web 仪表盘，用 React Flow 渲染交互式图谱 |

**生成的知识图谱保存在** `.understand-anything/knowledge-graph.json`，后续每次 `/understand` 只分析有变更的文件（增量更新），不用重新跑。

> 💡 对比一下：手写 PROJECT_MAP.md 是"手绘地图"，Understand-Anything 是"卫星遥感 + 自动制图"。
>
> 团队接手新项目或大型代码库时，先跑一遍 `/understand`，从"不知道有什么"变成"看到全局"。

### 3.2 跨模块依赖分析（3 min）

**场景**：要改 `src/services/order.ts`，怎么知道会影响哪些模块？

```
分析 src/services/order.ts 被哪些文件引用，
列出直接调用方和间接调用方。

如果我要修改 createOrder 的返回格式，
评估影响范围，列出需要同步修改的文件清单。
```

**关键价值**：AI 能快速做静态分析，人只需要评估业务影响。

**我的做法**：AI 带着方案来 → 我针对方案修正 → AI 用**架构、开发、测试、运维**四个角色综合方案和我的修正意见做评判 → 循环直到通过：

```
第一步：让 AI 先给方案，不要直接动手

"分析 src/services/order.ts 被哪些文件引用。
 如果我要修改 createOrder 的返回格式，
 列出影响范围和需要同步修改的文件清单。
 先给方案，不要改代码。"

第二步：我针对方案提出修正意见，然后 AI 四角色综合评判

"我的修正意见：
 1. 返回格式要和现有接口保持一致，不要引入新的字段名
 2. 前端调用方不止 order.ts，dashboard.ts 也引用了 createOrder

 综合你的方案和我的修正意见，从以下四个角色做方案评判：
 1. 架构：改动是否符合分层？会不会打破模块边界？
 2. 开发：改动量是否最小？有没有遗漏的调用方？
 3. 测试：哪些现有测试会受影响？需要补哪些测试？
 4. 运维：上线是否需要配置变更？是否需要数据迁移？

 逐个角色给出结论，有问题的继续修正，
 直到四个角色都通过为止。"
```

**提问纪律**（来自团队 lexy-workspace 实践）：

```
AI 带方案                我修正              AI 四角色评判
    │                      │                      │
    ▼                      ▼                      ▼
┌──────────┐  方案   ┌──────────┐  方案+  ┌──────────────┐
│ AI 分析   │ ─────→ │ 我审阅    │ ─────→ │ 架构视角      │
│ 提出方案  │        │ 提出修正  │  修正   │ 开发视角      │
│ 多个选项  │        │          │        │ 测试视角      │
└──────────┘        └──────────┘        │ 运维视角      │
                                         └──────────────┘
                                                │
                                        ┌───────┴───────┐
                                        ▼               ▼
                                   ✅ 全部通过      ❌ 有缺陷
                                   执行下一步       返回修正
                                                   继续评判
```

三条铁律：

| # | 规则 | ❌ 禁止 | ✅ 正确 |
|---|------|---------|---------|
| 1 | **一次一问** | 一条消息混入"确认+新问题+建议"，或一次抛 3+ 问题 | 聚焦一个话题 → 说明为什么 → 给选项 → 等确认 → 下一个 |
| 2 | **死循环停问** | 相同指令/错误重试 ≥5 次还在死犟 | 立刻停下来向用户报告：试了什么、什么原因、需要什么帮助 |
| 3 | **带方案来问** | "试了 5 次不行，你看看" | "试了 5 次，原因是 XXX。方案 A... 方案 B... 你选哪个？" |

> 💡 **核心理念**：AI 带方案，你给修正，AI 做评判。你不是审 AI 的代码——你是修正方向，AI 用四个角色帮你兜底。
>
> 四个角色的审视本质上是给 AI 做了一次**自我 Code Review**，大部分问题在这一步就能拦下来。

### 3.3 精确引用 vs 全量投喂（4 min）

**反模式**：让 AI "看整个 src/ 目录"

```
❌ 看看 src/ 下的代码，给我优化建议
```
→ AI 注意力分散，给出的建议泛泛而谈。

**正确做法**：精确引用相关文件

```
✅ 读以下文件，分析订单模块的性能瓶颈：
- src/services/order.ts（核心逻辑）
- src/models/order.ts（数据模型）
- src/api/order.ts（接口层）

重点关注：
1. 是否有 N+1 查询
2. 循环中是否有 DB 查询
3. 大对象是否全量加载
```

**原则**：一次给 AI 的文件不超过 5-10 个，总代码量不超过 500 行。

## 4. AI 辅助 TDD（10 min）

### 4.1 为什么需要 AI 辅助 TDD（2 min）

传统 TDD 的痛点：
- 写测试耗时，容易遗漏边界
- 人倾向于写 Happy Path 测试
- 需求变了，测试同步更新成本高

AI 能做什么：
- 根据需求自动生成测试用例（含边界）
- 根据失败测试生成实现
- 需求变更时自动建议测试更新

### 4.2 AI 辅助 TDD 流程（4 min）

既然已经是**文件传递上下文**的工作方式，标准流程就不是简单的"写测试→写代码→跑覆盖率"五步循环了。

以下是来自团队 lexy-workspace 实践的真实流程：

```
需求分析 ─→ todo文件拆分 ─→ 生成测试用例+验收条件 ─→ AI自动跑测试 ─→ 人验收页面
   │              │                    │                      │               │
   ▼              ▼                    ▼                      ▼               ▼
 analysis.md   todo-功能.md       acceptance-功能.md      npm test       浏览器验证
                              + __tests__/*.spec.ts    覆盖率报告       sign-off
```

**文件驱动的测试工作流**：

```
第 1 步：需求分析 → 生成分析文档

"分析 [功能需求]，列出所有场景和边界情况，
 写入 docs/tasklist/analysis-{功能名}-{日期}.md，
 包含：正常流程、异常流程、边界值、权限场景。
 先不要写代码。"

第 2 步：拆分 todo + 生成验收条件

"基于分析文档，生成两个文件：
 
 1. docs/tasklist/todo-{功能名}-{日期}.md
    - 任务按 Phase 编号（T1.1, T1.2...）
    - 每个任务含优先级、依赖、涉及文件、完成 checklist
    - 独立拆分测试任务（单元测试 / 集成测试 / E2E 测试）
 
 2. docs/tasklist/acceptance-{功能名}-{日期}.md
    - 验收用例按 AC-1, AC-2... 编号
    - 每条 AC 含：前置条件 → 操作步骤 → 预期结果
    - 末尾附验收签收表（前端/后端/测试负责人）
 
 验收条件要覆盖三层：
 - 单元测试层：工具函数 / composables / API 层
 - 集成测试层：API mock + 完整用户流程
 - E2E 测试层：Playwright 浏览器关键路径"

第 3 步：AI 按 todo 逐项实现 + 自动跑测试

"按 todo-{功能名}.md 的 T1.1 开始执行。
 每完成一个任务：写代码 → 跑对应的测试 → 更新 checklist → 报告结果。
 遇到测试失败，优先修复，不要跳过。"

第 4 步：人验收页面

"所有测试通过后，启动 dev server，
 对照 acceptance-{功能名}.md 的 AC 列表，
 在浏览器中逐条验证，签字确认。"
```

**关键原则**：

| 原则 | 做法 |
|------|------|
| **测试和验收条件同步生成** | 不是写完代码再补测试——todo 拆分时，测试任务和验收条件就跟开发任务一起产出 |
| **三层测试分层** | 单元测逻辑、集成测流程、E2E 测关键路径，不混在一起 |
| **AI 自动跑，人验收页** | 测试执行交给 AI，页面体验交给人。人不用盯着终端看测试结果 |
| **文件即状态** | todo 和 acceptance 文件就是进度载体，`/clear` 后读文件即可续传 |


### 4.3 Prompt AI 覆盖边界情况（2 min）

**常见问题**：AI 写的测试只有正常路径。

**解决方案**：在 prompt 中明确要求边界覆盖

```
生成单元测试时，必须包含以下边界情况：
1. 最小值 / 最大值
2. 空值 / null / undefined
3. 类型错误输入
4. 并发场景（如果适用）
5. 特殊字符 / 超长输入

用 describe.each 或 it.each 组织同类边界测试。
```

### 4.4 测试作为安全网（2 min）

**核心认知**：AI 生成的代码可能出错，测试是最后一道防线。

**工作流**：
1. 让 AI 改代码前，先确保现有测试能通过
2. AI 改完后，跑全量测试
3. 测试通过后才允许 Review

```
先跑 npm run test:unit，确认所有现有测试通过。
然后修改 src/services/order.ts 中的 createOrder 函数。
修改完成后，再次跑测试，确保没有破坏现有功能。
如果有失败的测试，优先修复，不要跳过。
```

## 5. Claude Code 深度工作流（8 min）

### 5.1 CLAUDE.md 进阶写法（3 min）

**基础版**（第 1 期已讲）：项目技术栈、代码风格、常用命令

**进阶版**：加入团队协作规范

```markdown
# CLAUDE.md — lexyAdmin 项目规范

## 技术栈
Vue 3.4 + TypeScript + Vite + Pinia + Element Plus

## 代码规范
- 命名：组件 PascalCase，函数 camelCase，常量 UPPER_SNAKE_CASE
- 类型：所有 API 入参出参必须定义 interface，放在 types/ 目录
- 注释：复杂逻辑用中文注释，说明"为什么"而非"做什么"

## 架构约定
- API 层：src/api/，统一用 http.request<T>(method, url, config)
- Store 层：src/store/modules/，用 defineStore，export useXxxStoreHook
- 视图层：src/views/，按模块分目录，组件放在对应 views/ 下的 components/

## 禁止事项
- 不要在组件里直接调 API，必须走 store action
- 不要用 any，类型不确定时用 unknown + 类型守卫
- 不要引入新的 UI 库，现有 Element Plus 已覆盖需求

## 测试要求
- 框架：Vitest
- 覆盖率：statements/branches/functions/lines >= 80%
- 新功能必须包含单元测试

## 常用命令
- npm run dev：启动开发服务器
- npm run test:unit：跑单元测试
- npm run typecheck：TypeScript 类型检查
- npm run precommit：提交前检查
```

**关键**：CLAUDE.md 不是一次性写完的，是在项目演进中不断追加的。

### 5.2 settings.json 实战（3 min）

Claude Code 的配置文件 `.claude/settings.json`：

```json
{
  "permissions": {
    "allow": [
      {
        "command": "npm run test:unit",
        "description": "运行单元测试"
      },
      {
        "command": "npm run typecheck",
        "description": "TypeScript 类型检查"
      }
    ]
  },
  "hooks": {
    "pre-commit": "npm run precommit"
  }
}
```

**作用**：
- `permissions.allow`：预先授权常用命令，减少每次的权限提示
- `hooks.pre-commit`：提交前自动跑检查，防止低级错误

### 5.3 高级命令速查（2 min）

| 命令 | 用途 | 场景 |
|------|------|------|
| `/ask` | 只提问，不改代码 | 想先理解代码再决定怎么改 |
| `/test` | 运行测试 | 改完代码快速验证 |
| `/commit` | 自动提交 | AI 完成一个完整功能后 |
| `/clear` | 清空对话上下文 | AI 变笨了，或开始新任务 |
| `/undo` | 撤销最后一次改动 | AI 改错了，快速回退 |

## 6. 完整功能开发演练（12 min）

### 演练目标

带一个真实需求走完整流程：**在 lexyAdmin 中实现"订单管理"模块**

以下流程来自团队 lexy-workspace 实践的 6 阶段标准，**不是 TDD**。

> 💡 先对齐需求、定方案，再拆分任务、写代码、验收。

### 6 阶段流程总览

```
深度调研 ─→ 需求对齐 ─→ 方案设计 ─→ 任务拆分 ─→ 开发执行 ─→ 验收测试
 AI执行    人机交互    人机交互    AI执行+人确认  AI执行+人Review  人工执行
   │          │          │           │             │            │
   ▼          ▼          ▼           ▼             ▼            ▼
现状报告   需求清单    定版方案    todo+acceptance  diff+功能    签字确认
```

### 流程演示

**Phase 1：深度调研（AI 执行，不改代码）**

```
需求：在 lexyAdmin 中增加订单管理功能，包含：
1. 订单列表页（订单号、客户名、金额、状态、创建时间）
2. 支持按状态筛选、按时间范围筛选
3. 支持导出 Excel
4. 订单详情弹窗

先读后端 API 文档、现有前端代码（views/hooks/api/mock/types），
输出现状报告：
- 哪些接口已就绪，哪些缺失
- 可复用的组件和参考页面
- 风险点和待确认事项

不要改代码，只输出报告。
```

**Phase 2：需求对齐（人机交互）**

```
基于现状报告，整理需求要点，
列出模糊问题逐个问我确认：
- 订单状态的枚举值有哪些？
- 导出 Excel 是否需要后端新接口？
- 详情弹窗是路由跳转还是 Dialog 弹窗？
- 筛选条件是否需要持久化到 URL？

一次只问一个，等我回应后再下一个。
全部确认后，输出确认的需求清单。
```

**Phase 3：方案设计（人机交互）**

```
需求已确认。给出方案，包含 5 部分：
1. TypeScript 接口定义（入参/出参）
2. 文件树（新增/修改哪些文件）
3. 模块详情（每个文件负责什么，参照哪个现有文件）
4. API 调用链路（页面 → store → api → 后端）
5. 关键决策备忘（为什么这么设计）

先给方案，等我确认后再进入下一步。
```

**Phase 4：任务拆分（AI 执行，人确认）**

```
方案已确认。生成两个文件：

1. docs/specs/todo-订单管理-refactor.md
   - 任务按 Phase 编号（T1.1, T1.2...）
   - 每个任务含优先级、依赖、涉及文件、完成 checklist
   - 开发顺序：API类型+Mock → 独立组件 → Hook+页面整合 → 运营功能 → 验证

2. docs/specs/acceptance-订单管理-refactor.md
   - 验收用例按 AC-1, AC-2... 编号
   - 每条含：前置条件 → 操作步骤 → 预期结果
   - 末尾附验收签收表

先把两个文件内容展示给我确认，确认后再写入。"
```

**Phase 5：开发执行（AI 执行，人 Review）**

```
按 todo-订单管理-refactor.md 的 T1.1 开始执行。
每完成一个任务：
1. 先说明要做什么，等我确认
2. 写代码（先 API/Mock，再组件，再页面整合）
3. 跑 typecheck + lint + 测试，对照验收条件自检
4. 更新 todo 状态为 ✅
5. 报告结果，等我确认后继续下一个

改完代码后展示 diff，AI 不直接提交。
```

**Phase 6：验收测试（人工执行）**

```
所有任务完成，启动 dev server。
对照 acceptance-订单管理-refactor.md 的 AC 列表，
在浏览器中逐条验证：
- ✅ 正常流程
- ✅ 异常流程（空数据、网络错误）
- ✅ 边界情况（超长订单号、特殊字符）
全部通过后，验收签收表签字确认。
```

## 附录 A：讲师备忘 — 常见问题应对

### Q1：学员说 "AI 生成的测试质量不高"

**回应**：测试质量取决于 prompt 的质量。给 AI 明确的边界要求（"必须覆盖 null/空数组/超大数"），质量会显著提升。另外，AI 是生成初稿，人必须 Review 和补充。

### Q2：学员说 "我们的项目没有测试，怎么开始 TDD"

**回应**：不是从零开始 TDD。可以先用 AI 给**现有代码**补测试（作为安全网），然后再用 TDD 开发新功能。

### Q3：学员说 "CLAUDE.md 写了很多，AI 还是记不住"

**回应**：检查两点：
1. CLAUDE.md 是否在项目根目录
2. 内容是否过长（超过 500 行可能超出上下文）

解决方案：拆分为多个文件，`CLAUDE.md` 放核心约定，具体模块的规范放在 `docs/standards/` 下，需要时让 AI 读。

### Q4：学员说 "AI 改代码把别人的功能弄坏了"

**回应**：这是没有跑全量测试的后果。养成习惯：**改前跑测试 → 改后跑测试 → 测试通过才提交**。用 `settings.json` 的 `pre-commit` hook 强制执行。
